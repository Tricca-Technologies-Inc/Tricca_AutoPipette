# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Tricca AutoPipette controls an automated liquid handling system (ALHS) built on the Voron 3D-printer/Klipper platform. A long-running control daemon (`tapd`) owns the single connection to a Moonraker instance running on the machine's controller board (Manta) — sending JSON-RPC/G-code over WebSocket to drive the gantry, syringe pump, and tip-ejection servo — and exposes a local control-plane WebSocket that two thin clients talk to: a `cmd2`-based interactive shell (`tap`) and a FastAPI "kiosk" touchscreen web UI for non-interactive protocol runs. Neither client connects to Moonraker directly. `tapd` itself has no cmd2/CLI framework in it at all — it's a plain `AutoPipetteService` object plus an `aiohttp`-based control-plane server; cmd2 only exists in the two client processes.

The root `README.md` is a thin front door (quickstart + links) — this file is the architecture deep-dive it links out to, and is where current structure should be confirmed.

This file describes the system as it **is**. Planned-but-unimplemented work lives in **GitHub Issues** — start from the backlog map (issue #34), which carries the dependency order, the standing findings, and an index of every entry. Check it before starting anything non-trivial, since several issues record decisions already taken and open questions that must be settled first. The backlog also flags problems that are true of the code *today*. Note that neither `tapd`'s control plane nor the kiosk has **any** authentication — both are protected solely by binding loopback, so treat any change to a bind address as a security decision (see `systemd/README.md` and `docs/adr/0002-loopback-only-trust-boundary.md`). `tapd` enforces this fail-closed: `daemon/main.py`'s `check_bind_host` refuses a non-loopback `--host` unless `--allow-insecure-bind` is passed. The kiosk has no such guard (its bind is uvicorn's own `--host`), so its systemd unit's `127.0.0.1` is the only thing keeping it local.

## Commands

```bash
# Install: uv (https://docs.astral.sh/uv/) syncs .venv from the committed
# uv.lock -- runtime deps have loose bounds in pyproject.toml, the exact
# versions live in uv.lock (issue #24). Every command below goes through
# `uv run`, which uses that .venv.
uv sync --extra dev                        # dev: editable install + dev tools
uv sync --extra dev --extra browser-test   # + pytest-playwright (then: uv run playwright install chromium)
uv sync --frozen                           # production: exactly what uv.lock says, no dev tools
uv lock                                    # after editing dependencies in pyproject.toml; commit uv.lock

# Run the control daemon first -- tap and the kiosk are both clients of it
# and do nothing useful until it's running.
uv run tapd                          # connects to hostname/IP from the active local system config (see "Multi-machine config split" below)
uv run tapd --no-connect             # start without a Moonraker connection (local testing)
uv run tapd --local-connect          # connect to ws://localhost/websocket (e.g. local Moonraker/mock)
uv run tapd --config <name>          # load a named local system config profile by name (resolved under the local root's system/, never config/)
uv run tapd --init-local-config [name] # bootstrap a local system config profile from the shared template, then exit
uv run tapd --host / --port          # control-plane bind address (default 127.0.0.1:8765); non-loopback host refuses to start...
uv run tapd --allow-insecure-bind    # ...unless this is passed too (bare acknowledgment, logs a loud warning -- see ADR-0002)
uv run tapd --log-level DEBUG

# Run the interactive shell (a thin tapd client -- start tapd first)
uv run tap                           # connects to ws://127.0.0.1:8765/control by default
uv run tap --control-uri <uri>       # point at a different tapd instance
uv run tap --log-level DEBUG

# Run the kiosk web backend (also a tapd client).
# Loopback only -- the kiosk has no authentication; see systemd/README.md.
uv run uvicorn autopipette_kiosk.main:app --host 127.0.0.1 --port 8000

# Lint / format / type-check
uv run ruff check .
uv run ruff format .
uv run pyright

# Tests
uv run pytest                         # unit/integration tests under tests/ (pythonpath=src, testpaths=tests+src in pyproject.toml)
uv run pytest --doctest-modules       # same, plus executing every >>> doctest example under src/ as a test

# Docs (Sphinx; requires the `dev` extra)
uv run sphinx-build docs docs/_build/html          # regular build
uv run sphinx-build -W docs docs/_build/html       # warnings-as-errors -- run this before a docs-affecting PR
```

Inside the `tap` shell, protocol files (`.pipette`, plain text — one shell command per line, blank lines allowed) are run with `run <path>`; the command grammar is exactly the shell's own, so `commands/tap_cmd_parsers.py` is the authoritative reference for what a line may contain. The `protocols/` directory was cleared out and its remaining contents are not a reliable syntax reference — check a file against the parsers before assuming it runs. `run` executes each line in batch mode, buffering G-code, then uploads and executes it as a single file on the pipette — all of this happens inside `tapd`, which every `tap` command (not just `run`/`cancel`/`pause`/`resume`) dispatches to over the control-plane connection via a structured RPC.

## Architecture

### Three components, one core library
- `src/tricca_autopipette/` — the hardware-control core, the `tapd` daemon, and the interactive shell.
  - `daemon/` — `tapd` (entry point `daemon.main:main`), a long-running process that owns the single persistent Moonraker connection and exposes a local control-plane WebSocket (`ws://127.0.0.1:8765/control` by default) that both `tap` and the kiosk talk to instead of connecting to Moonraker themselves. See "The `tapd` daemon" below. There is no cmd2 anywhere in this process.
  - `cli/` — `tap` (entry point `cli.main:main`) instantiates `cli/remote_shell.py`'s `RemoteTapShell`, a `cmd2.Cmd` whose `do_*` methods are all thin wrappers around control-plane RPC calls; it owns no `AutoPipette`/Moonraker connection itself. A separate standalone `cmd2.Cmd` (`cli/tap_shell.py`'s `TriccaAutoPipetteShell`) used to exist for local one-off scripting/testing, constructing its own `AutoPipetteService` with its own direct Moonraker connection; it was removed in issue #39 once `RemoteTapShell` reached full command parity with it. A caller that still wants a zero-daemon REPL drives `AutoPipetteService`'s plain sync API (`connect`/`disconnect`/`run_protocol_blocking`) directly from a plain Python shell or script instead.
  - `core/`, `commands/`, `moonraker/` — the domain model, shared command-parsing helpers (`commands/tap_cmd_parsers.py`, used by both `RemoteTapShell` and the daemon), and Moonraker transport.
- `src/autopipette_kiosk/` — a thin FastAPI app (`main.py` + a multi-page `static/` frontend, see "Kiosk frontend" below) exposing `GET /protocols` (lists `.pipette` files via a local directory glob — the one thing it still does without the daemon), `POST /run` (calls the daemon's `run.start`), `POST /home` (calls `movement.init`), `POST /move`/`POST /move_loc`/`POST /move_rel` (the Move page, issue #86, over `movement.move`/`move_loc`/`move_rel`; a raised daemon exception — not-homed, unknown location — maps to an HTTP status via `_translate_move_error`, the same shape `/run` uses), `POST /breakpoint/respond`, `GET /status`, `WS /ws/status` (re-broadcasts the daemon's `notify_run_status`/`notify_breakpoint` pushes to connected browsers, event-driven rather than polled — also relays a raw Moonraker `notify_status_update` for live toolhead position/homed-axes, via `ws.subscribe`, so the Move page's banner and position readout update without polling), `GET /tips`/`POST /tips/reset`/`POST /tips/set` (routing-only wrappers around `config.tips`/`config.reset_tips`/`config.set_tips`, issue #17), and the Settings page's `GET /settings`/`POST /settings/set`/`POST /settings/load_pipette`/`POST /settings/switch_system`/`POST /settings/load_liquid`/`POST /settings/unload_liquid` (routing-only wrappers around `config.settings`/`set_value`/`load_pipette`/`switch_system`/`load_liquid`/`unload_liquid`, issue #33 slice c). `/ws/status` also carries `config_locked` from each `notify_run_status` push. It holds one persistent `WebSocketClient` connected to `tapd`'s control plane for the app's lifetime (FastAPI `lifespan`), and reports real completion — driven by Moonraker `print_stats` transitions — rather than inferring it from a subprocess's exit code. Unlike `/run`/`/home` (which translate a *raised* daemon exception to an HTTP status), the `/tips*` and `/settings*` routes (plus `GET /locations`, shared by the Deck page's spatial map, issue #87, and the Move page's location dropdown, issue #86) forward `CommandResult`'s `{ok, message, data}` as-is (via the shared `CommandResultResponse` model) since those RPCs report failure as `ok=False`, not by raising.
- `systemd/` — unit files for both processes (`tapd.service`, `autopipette-kiosk.service`, the latter `Requires=`/`After=` the former) plus an install README.

**Client parity rule.** Every capability reachable from the kiosk must also be reachable from `tap`, and vice versa — neither client may be the only way to do something. This is nearly free if capability lands as an `AutoPipetteService` method plus a `ControlRequests` builder: both clients are thin adapters over the same control-plane RPCs, and `tap` picks it up by adding one hand-written `do_*` method to `RemoteTapShell` (`cli/remote_shell.py`). `tests/cli/test_remote_shell_dispatch_completeness.py` guards this mechanically — every `ControlRequests` builder must appear in that test's builder→command map (or its short by-design exclusion list), so a new builder with no matching `do_*` fails CI instead of silently reopening the gap. The way to break parity is adding logic directly in `autopipette_kiosk/main.py`, which produces a kiosk-only capability with no RPC behind it, invisible to `tap` and to protocol files. `main.py` holds exactly one such thing today — the `/protocols` directory glob — and that is the shape to avoid repeating. Remaining gaps are tracked as issue #28.

### Kiosk frontend (`autopipette_kiosk/static/`)
A multi-page shell (issue #25), vanilla HTML/CSS/JS — no build step, no framework. `index.html` holds both pages' markup together (each a `.page` container, shown via a CSS `active` class); only styling and behavior are split out, into `style.css` and one JS module per concern:
- `app.js` — the shell. Owns the single `/ws/status` WebSocket connection and the shared run-status/breakpoint state, exposed to page modules via `App.onStatus(fn)` rather than letting each page touch the socket itself — a real page navigation would drop and re-establish that connection mid-run, which is why switching is client-side (toggling `active` classes) and not a server-rendered separate page. Also owns the global header chrome (connection indicator, Home button, a compact run-status pill, and the breakpoint banner with Continue/Abort) — all visible regardless of which tab is active, since an operator correcting tip inventory on the Tips tab must still see and answer a paused breakpoint without switching tabs — and the tab switcher itself: a small data-driven registry (`App.registerPage(id, {onShow, onHide})`), not hardcoded branches, so a new page is a registry addition rather than a rewrite. A full page reload always lands back on the Run tab (no persisted tab state in `localStorage`/a URL fragment); the monitoring view is what a reload should show, not wherever an operator happened to be.
- `run.js` — the Run page: protocol list, run button, the *detailed* status card (icon/state/message/progress bar). Subscribes to `App.onStatus` rather than owning any connection state.
- `tips.js` — the Tips page (issue #17): renders `TipBoxManager.describe`'s per-box payload (via `GET /tips`) as a grid — the same data `cli/report_tables.py`'s `build_tipbox_map` renders as ASCII for `tap`, so this is a second renderer, not a second implementation. A "Reloaded" button per box calls `POST /tips/reset`; tapping a grid cell toggles it and calls `POST /tips/set` immediately (optimistic update, reverted on failure) — auto-save per tap rather than a batched "Apply," since `config.set_tips` already replaces a box's *entire* state on every call (declare-exact-state, not incremental), so there's no cheaper granularity to batch toward. Masked-out positions (present in `num_row × num_col` but outside the box's `eligible` set) render dimmed and aren't tappable. Grid content is greyed out client-side while a run is active (polling the shared status via `App.onStatus`) — a UI nicety, not a new server-side guard; nothing in `daemon/service.py` was touched to add this.
- `move.js` — the Move page (issue #86): D-pad jog (`POST /move_rel`), absolute-coordinate move (`POST /move`), and a named-location dropdown (`POST /move_loc`, populated from `GET /locations`) — three thin adapters over the daemon's `movement.*` RPCs, plus a live position/homed banner relayed over the shared `/ws/status` stream. All three fire immediately on tap, no confirmation dialog (jog/goto aren't destructive, a stray tap is correctable with another) — except the absolute-move "Go" button, which validates all three X/Y/Z fields are actual finite numbers first, rather than defaulting a blank/mid-edit field to 0 and firing an unconfirmed move on a live machine.
- `deck.js` — the read-only Deck page (issue #87): a spatial map of the configured deck (`GET /locations` for placement, `GET /tips` for tipbox occupancy), for visually verifying plate/tipbox/waste-container position before a run. `toPercent()` maps a location's real mm coordinates onto the deck's 40×40cm square with the machine origin at the square's top-right corner and X increasing moving away from that corner (confirmed against `config/locations/examples_deck.json`'s real coordinates, not an assumption from per-plate well-spacing math — an earlier, wrong sign put every real example position off the square's edge). Tapping a tipbox tile switches to the Tips tab for editing; this page never mutates anything itself.
- `settings.js` — the Settings page (issue #33 slice c): a renderer over `GET /settings` (`AutoPipetteService.settings`), which lists the system profiles, the active pipette (with every pipette file to swap to) and gantry fields, and every loaded liquid, each field carrying its live value, its bounds, and the `category`/`filename`/`key_path` an edit must go to (`JsonConfigManager.setting_source` resolves that: a gantry block or liquid override in the system file, or the `extends` parent that supplies it, wins over the category file). A field edit posts that target back to `POST /settings/set`, so the page holds no config logic. Pipette and gantry fields are high-risk: `min`/`max` come from `core/config_writer.py`'s `HIGH_RISK_BOUNDS` (enforced again server-side on every write), and Save checks the bounds and then asks for an inline Confirm. Liquid fields save on change with no confirm (empty = `null`, defer to the pipette). A pipette/gantry save, `load_pipette` or `switch_system` shows a "Home required" banner, since each invalidates homing. While `config_locked` is set on the shared status (`App.onStatus`), every control is disabled and a banner reads "Locked while a protocol is running."; a write refused with `data.reason == "run_active"` shows the same text, and any other `ok=False` shows its `message` under the field. Locations stay on the Deck page and aren't edited here.
- Verify (a Run-tab "Check" button surfacing `run.validate`'s findings, issue #88, following on from #36) is planned but not yet built — deliberately not a fourth page (see issue #88), so it isn't a `App.registerPage` entry like the others above.

### The `tapd` daemon (`daemon/`)
- `service.py` — `AutoPipetteService`: the single business-logic/application-service object. Builds its own `AutoPipette` (domain layer), `WebSocketClient`/`MoonrakerRequests` (the one Moonraker connection), and `GCodeManager` directly in `__init__` — there is no intermediate shell object of any kind. Every command (`move`, `aspirate`, `switch_liquid`, `ls`-equivalents, WebSocket diagnostics, run lifecycle, ...) is a plain typed method here, taking one of `commands/tap_cmd_parsers.py`'s `*Args` dataclasses (or a bare value) and returning a `CommandResult` (`ok`/`message`/`data`). `control_server.py` dispatches control-plane RPCs straight to these methods (via `dataclasses.asdict`) — the sole driving adapter, now that issue #39 removed the standalone shell's cmd2 `CommandSet` adapters that used to call these methods in-process too.
  - Async, non-blocking API for the daemon (used by `control_server.py`): `start`/`stop` (connect/disconnect without blocking the event loop, via `asyncio.to_thread`), `start_run`/`cancel_run`/`pause_run`/`resume_run`/`stop_run`, `dispatch` (runs a sync method under the service's lock, in a worker thread), `request_breakpoint`/`confirm_breakpoint`, `ping`.
  - Plain sync counterparts for standalone/local-scripting use (a caller with no event loop driving this class directly, since issue #39 removed the standalone `TriccaAutoPipetteShell` that used to be the entry point for this): `connect`/`disconnect`, `run_protocol_blocking` (blocks until the protocol finishes, reusing the exact same per-line dispatch loop `start_run` uses), and the underlying `send_cancel`/`send_pause`/`send_resume`/`emergency_stop` Moonraker calls the async wrappers just run via `asyncio.to_thread`.
  - `start_run` returns as soon as the run is *started*, not when it finishes: the actual protocol replay runs as a background task rather than being awaited inline, since a `break` line can pause for an arbitrarily long time waiting on a remote client and the `run.start` RPC itself must not block on that.
  - `cancel_run`/`pause_run`/`resume_run`/`stop_run` deliberately bypass the service's dispatch lock — they only send a Moonraker control RPC, never touching the G-code buffer or `AutoPipette` domain state, and must be able to interrupt a run that's stuck (e.g. paused at a breakpoint, which holds the lock for the run's whole duration).
  - `_run_protocol_sync`/`_dispatch_protocol_line` replay a `.pipette` file by tokenizing each line (`shlex.split`) and looking it up in one of two module-level dispatch tables (`_LINE_DISPATCH` for parser-backed commands, `_STR_ARG_DISPATCH` for the handful taking one bare string like `switch_liquid`) built from the exact same data `control_server.py`/`commands/tap_cmd_parsers.py` already define — one source of truth for "command name → parser → service method," not three. `break` is special-cased to call `request_breakpoint` directly. An unrecognized command name reports `CommandResult(ok=False, ...)` rather than raising (preserves old tolerant behavior for typos in committed protocol files), but any exception a *recognized* command's method raises aborts the rest of the batch.
  - `_run_startup_script` replays `core/.init_pipette` once via that same per-line dispatch, on `connect()`/`start()` — a startup script, without cmd2's `startup_script`/`cmdloop()` mechanism this class has no access to.
  - `domain_state_snapshot` (issue #35) is a context manager wrapping `_run_protocol_sync`'s dispatch loop: a line that raises is a *compile-time* failure (nothing physical has happened yet, since G-code only uploads after every line dispatches), rolled back to exactly the pre-enter deck/pipette state — which locations/tipboxes are registered at all (`LocationManager.snapshot_membership`/`restore_membership`, undoing `del_loc`/`clear_locs`/`load_locations`/`unload_locations`), every tipbox's consumed-position map, every plate's traversal cursor, and tip/liquid state, in that order (membership first, so a same-name mid-run reconfiguration is fully undone rather than merely detected). A *runtime* failure (after upload) is deliberately not caught here at all. The `persist_tip_presence`/`persist_tip_liquid_state` decorators defer their Moonraker DB writes while `gcode_manager.is_batch_mode`, so a rollback never has to undo a durable write, just flush the final state once on success. `restore="always"` (issue #36's dry-run use) restores unconditionally regardless of outcome.
  - `validate_protocol` (issue #36) dry-runs a `.pipette` file through the same `_LINE_DISPATCH`/`_STR_ARG_DISPATCH` tables and `_dispatch_protocol_line`, but on-demand only (`run.validate`/`tap`'s `validate <file>`, never implicit before a real `run.start`) and catch-and-continue rather than stop-at-first: `_dispatch_protocol_line_for_validation` records each line's outcome as a finding (`{line_number, command, severity, message}`, severity `error`/`warning`/`info`) instead of letting an exception abort the batch, so both `NotALocationError` and `VolumeCapacityError` — and a WARNING the domain layer logs, e.g. `fit_air_volumes` shrinking an air gap, captured via a scoped `logging.Handler` — fall out of the real dispatch for free; no separate per-line location/volume checks were added. The whole replay runs inside `domain_state_snapshot(restore="always")` (issue #35) plus a module-level `_dry_run` `ContextVar` that short-circuits `require_homed`/`persist_tip_liquid_state`/`persist_tip_presence` for its duration, so validation works on an unhomed machine and never uploads G-code, writes a file, or persists to Moonraker's database. `break` and `save_locations` are intercepted before reaching the real dispatch tables — recorded as an `info` finding and skipped, never actually blocking or writing a file.
- `moonraker_state.py` — `MoonrakerStateTracker`: subscribes to Klipper's `toolhead`/`print_stats` objects (`printer.objects.subscribe`) and tracks live `homed_axes` (for the interlock) and job completion (mapped onto run status) from real Moonraker pushes, rather than a locally-set flag or a subprocess exit code. Also persists tip/liquid state (`tip_state`, `has_liquid`, `current_liquid`) through Moonraker's `server.database` API so it survives daemon restarts — Klipper has no native notion of "is a pipette tip attached," so unlike homed-axes tracking this is a durability layer only, not a live-hardware-truth source.
- `control_server.py` / `control_requests.py` — the control-plane WebSocket server and its pure-function JSON-RPC request builders (`ControlRequests`, mirroring `MoonrakerRequests`'s shape and envelope). Method namespaces: `movement.*`, `pipette.*` (`transfer` for the `pipette` command, avoiding a `pipette.pipette` stutter), `config.*` (mutating commands, including `set_value`/`unload_liquid`/`load_pipette`/`switch_system` which are run-locked, plus `list_locations`/`list_plates`/`list_liquids`/`system_summary`/`settings` reporting), `util.*`, `run.*` (`start`/`status`/`cancel`/`pause`/`resume`/`stop`/`confirm_breakpoint`/`validate`), `ws.*` (WebSocket/Moonraker diagnostics: `status`/`ping`/`send`/`notify`/`subscribe`/`unsubscribe`/`upload`/`read`/`read_all`/`clear_queue`/`reconnect`), `protocols.list`, `daemon.ping`/`identify`/`clients` (`identify` tags a connection with its client type for the RPC log, issue #53; `clients` lists currently-connected client types, issue #59 — both are audit-trail/debugging aids, not access control). Pushes: `notify_run_status`, `notify_breakpoint`, `notify_raw_event` (relays a `ws.subscribe`d raw Moonraker notification to every connected control-plane client, since an arbitrary client-side callback can't itself cross the wire). There's a dispatch-completeness test (`tests/daemon/test_control_server_dispatch_completeness.py`) asserting every `ControlRequests` builder has a matching `_call` branch.
- `main.py` — the `tapd` entry point; parses the `--config*`/`--no-connect`/`--local-connect` flags the old `tap` used to (they now configure the daemon's Moonraker connection, not a CLI client). Validates config file paths via `core/config_validation.py`'s `validate_config_files` — moved there from `cli/main.py`, which no longer loads config files at all.

Control-plane clients (kiosk, `tap`) reuse `moonraker/websocket_client.py`'s `WebSocketClient` unmodified as their transport — the control-plane envelope is deliberately isomorphic to Moonraker's own, so the same client class works for both hops.

### Homed-safety interlock
Backed by live Moonraker state, not a locally-mutated flag: `daemon/service.py`'s `require_homed(command_name)` decorator (applied directly to the gated `AutoPipetteService` methods — `move`, `move_loc`, `move_rel`, `transfer`, `aspirate`, `dispense`, `next_tip`, `eject_tip`, `dispose_tip`, `change_tip`) checks `self.moonraker_state.is_homed()` and raises `core/pipette_exceptions.py`'s `NotHomedError` if unset/false. `home`/`init` are exempt (they're what performs homing). Since the decorator wraps the whole method, the homed check always runs *before* any "soft precondition" short-circuit the method body itself might otherwise check first (e.g. `move_rel`'s all-zero-offset no-op) — deliberately, for consistent behavior across every gated method.

This one check now covers every call path uniformly — `RemoteTapShell` (via the control plane), the daemon's protocol-file dispatch loop, and direct `ControlServer` RPCs all go through the same decorated method, so there's no separate hook to keep in sync (a prior interactive-shell-only `precmd` hook was broken against the installed cmd2 4.0 API and never actually blocked anything; the now-removed standalone `TriccaAutoPipetteShell` got the real check too before issue #39 deleted it, closing that gap). `_run_protocol_sync` aborts the whole remaining batch if a gated line raises `NotHomedError` (or anything else) rather than skipping just that line — protocol files aren't expected to include their own leading `home all`/`init` line, so home the machine once via the kiosk's Home button, or `tap`'s `init`/`home all`, before running them; `homed_axes` then stays true for the rest of the daemon's uptime — unless a live pipette/gantry/system change invalidates homing (see "Live config changes" below). There is no `--skip-homed-check` flag — it was a blanket per-process bypass that never actually verified physical homing state, superseded by checking the real thing.

A matching `persist_tip_liquid_state` decorator (same file) persists tip/liquid state to Moonraker's database via `MoonrakerStateTracker.save_tip_liquid_state` whenever it actually changed, applied to the same gated methods plus `init`/`home`/`switch_liquid`/`load_liquid` — this also closes a gap a hook-based approach would have: every call path (RPC, protocol-file line, interactive) persists identically, since it's the method itself that's wrapped.

A sibling `persist_tip_presence` decorator (same file) does the same for the *other* piece of state Klipper has no notion of — which tip positions are still occupied — applied to `transfer`/`next_tip`/`change_tip` plus the location-loading and tip-inventory commands. It writes `TipBoxManager.snapshot()` under the `tip_presence` DB key, and only when the snapshot actually changed.

### Location loading and tip inventory
`LocationManager.load_from_json` is **additive** — loading a second file adds to the deck rather than replacing it, so a deck composes from reusable groups. `--replace`/`replace=True` opts into the old wipe-then-load. Everything is parsed and validated *before* anything is applied, so a missing file or a malformed entry leaves the existing deck untouched (it used to `clear()` first and validate second, wiping the deck on a mistyped filename). A duplicate name is last-load-wins with a WARNING naming both source files, tracked via `LocationManager._sources`/`source_of`.

Names are the sole identifier: `set_plate` no longer also files a waste container under the literal alias `"waste_container"`, which stored one plate under two names.

Tipboxes are registered with `core/tipbox_manager.py`'s `TipBoxManager` (see below) rather than merged, so `unload`/`del_loc` removes exactly one box and leaves every other box's consumed-tip state intact. `AutoPipette.next_tip` asks the manager for `(name, box, coord, index)`, takes the dip distance from *that* box — boxes may sit at different heights — and records `(name, index)` as `PipetteState.tip_origin` (cleared by `eject_tip`, so by every eject/dispose/return; snapshotted by `domain_state_snapshot` too). It lives in memory only, so a tip already on when `tapd` starts has no origin.

Because Klipper has no notion of tip occupancy, the operator reconciles the daemon's record with the physical boxes via `tips` (ASCII map; `--db` diffs it against the persisted state and flags divergent cells), `reset_tips <box>`/`reset_tips_all` (a fresh box was loaded), and `set_tips <box> <ranges> [--available]` (declare exact state — absolute, not additive, so it can restore positions too). A locations entry may also declare a partially-used box up front with `"tips": {"consumed": ["A1:C12"]}`.

**Where a tip goes after a transfer (issue #15).** `pipette --tip_end keep|waste|return` (`PipetteArgs.tip_end`, `AutoPipette.pipette`/`pipette_splits`' `tip_end`, `AutoPipette.finish_tip`) and `change_tip --tip_end waste|return`. Default is `waste`. `return` (`AutoPipette.return_tip`) puts the tip back in the exact slot it came from and marks that slot `TipSlotState.USED`. `next_tip` never hands out a `USED` slot again; only `set_tips --available`, a kiosk tap, or `reset_tips` clears it. `AutoPipette.dispose_tip` falls back to returning the tip to its origin, with a WARNING, whenever no waste container is configured. That covers every caller: an explicit or defaulted `waste`, `change_tip`, and a bare `dispose_tip` line. It raises `NoWasteContainerError` only when the origin is also unknown, and `return` with no origin raises `NoTipOriginError`. There's no implicit pre-run waste-container check. Instead, the fallback WARNING is logged through the domain logger, so `validate_protocol` reports it as a finding with no extra code. `--keep_tip` is a permanent, deprecated alias for `--tip_end keep`, since 119 `protocols/legacy/` files use it. `AutoPipette.resolve_tip_end` logs a WARNING on every use (also a `validate_protocol` finding) and raises `ValueError` if it conflicts with `--tip_end`. Do not add a "just eject it here" fallback: dropping a used tip over a sample plate is the failure mode this design removes.

Tip slots are tri-state: `TipSlotState` (`core/pipette_models.py`) is `AVAILABLE`/`USED`/`EMPTY`, stored as `TipBox.slots`. `TipBox.present` is the derived binary view. `TipBoxManager.snapshot` persists `slots`, and `restore` still accepts a pre-#15 `present` bool list (True→`AVAILABLE`, False→`EMPTY`). Manual correction stays binary: `set_consumed`/`set_tips` and the kiosk tap assert available-or-not, and a listed slot that is already `USED` stays `USED`. `describe` emits both `present` and `slots`. `tips` renders `USED` as `u`, and the kiosk's Tips and Deck grids render it amber.

### `RemoteTapShell` (`cli/remote_shell.py`)
The actual `tap` CLI. A `cmd2.Cmd` with no `CommandSet`s and no domain/Moonraker objects of its own — every `do_*` is an individually hand-written method, a few lines each: parse args (via `@with_argparser`/a bare `Statement`), build a `ControlRequests` request, dispatch it through the shared `_call_and_print`/`_send` helpers, render the JSON response. Commands were briefly generated instead from a declarative table, but that made `help -v`'s one-line summaries — and, for the handful of no-argument commands, `help <cmd>` too — show a generic templated string rather than real text: cmd2 only renders a command's `Cmd2ArgumentParser` description for `help <cmd>` on argparse-backed commands specifically; every other help surface (`help -v`'s summary column, `help <cmd>` on a no-argument command) reads the `do_*` function's own docstring directly, which a generic per-row template can't supply. Hand-writing costs a few dozen near-duplicate methods but keeps every command's help genuinely useful, and `tests/cli/test_remote_shell_dispatch_completeness.py` (see "Client parity rule" above) replaces the generated table's implicit one-row-per-command completeness guarantee with an explicit, checked one. Grouped under banner-comment sections mirroring the command categories (movement/pipette/configuration & locations/protocol lifecycle/utility/WebSocket & daemon diagnostics/reporting). There is no `shell.exec`/generic-forwarding fallback — every command maps to a real control-plane RPC, and an unrecognized command falls through to cmd2's own built-in "unknown command" handling.

Argparse parsers/arg dataclasses for commands live centrally in `commands/tap_cmd_parsers.py` (`TAPCmdParsers`), not next to each `do_*` method; `args_from_namespace` (same file) converts a parsed `Namespace` into the matching `*Args` dataclass, shared by `RemoteTapShell` and `AutoPipetteService`'s protocol-file dispatch. `ls`/`list_liquids` call the service's data-only reporting methods (`list_locations`/`list_plates`/`list_liquids`/`system_summary`) and render the result as a `rich.table.Table` via `cli/report_tables.py`.

A standalone `cmd2.Cmd` (`cli/tap_shell.py`'s `TriccaAutoPipetteShell`) used to exist alongside `RemoteTapShell` for local one-off scripting/testing, built from `CommandSet` subclasses (`commands/*.py`) over the exact same `AutoPipetteService`. It was removed in issue #39 once `RemoteTapShell` reached full command parity with it — verified command-by-command before the removal, with `break` (a synchronous block-and-wait idiom that only made sense in that shell's local blocking model) confirmed as not a real gap, since `RemoteTapShell`'s control-plane-native equivalent (an async `notify_breakpoint` push, answered with `continue`/`abort`) is the correct shape for the same functionality over a control-plane connection.

### Config system (layered JSON, see `config/README.md`)
`JsonConfigManager` (`core/json_config_manager.py`) loads and merges:
- `config/system/*.json` — top-level, references network settings, gantry, pipette model, liquids, and the deck layout (`locations`). A config may `extends` another system file, shallow-merged per top-level key (cycle- and depth-guarded), so a per-protocol config carries only what differs — usually just `locations` — instead of duplicating machine settings that would then drift.
- `config/gantry/*.json` — kinematics (speeds/accel)
- `config/pipettes/*.json` — syringe kinematics, servo angles, volume capacity, and the required `syringe.max_travel_mm` (issue #29): the manufacturer-stated plunger travel, used only as the endstop-move distance — homing and `clear_syringe` drive `2 * max_travel_mm` toward the endstop with `STOP_ON_ENDSTOP=home` (deliberate overshoot; Klipper stops at the trigger), no calibration curve involved. It sits *alongside* `max_volume_ul`/`capacity_margin_ul`, which stay the µL capacity/chunking limits. It has no default: a pipette file without it fails validation naming the field (a system config referencing such a file re-raises that `ValidationError` rather than a bare "Unknown pipette"), so every local pipette config needs it added by hand.
- `config/liquids/*.json` — per-liquid overrides (viscosity, speeds/waits, prewet and air-gap technique, optional custom calibration curve) merged on top of the pipette's base syringe kinematics — see "Pipetting technique" below
- `config/locations/*.json` (parsed by `LocationManager`, `core/location_manager.py`) — named coordinates and plate placements, including special `tipbox`/`waste_container` plate types, plus per-plate `order`/`mask`/`on_exhaust`/`tips`
- `config/plates/*.json` — reusable plate templates (dimensions, well layout, dipping strategy), instantiated via `PlateFactory` in `core/plates.py` (registry-based: `Plate` → `PlateArray`/`PlateSingleton` → `TipBox`/`WasteContainer`)

Filenames not paths are passed around at the shell/CLI layer — `DefaultPaths`/`DefaultFilenames` (`core/pipette_constants.py`) resolve them against `DefaultPaths.DIR_REPO_ROOT` — four levels up from `pipette_constants.py`, which is only correct for a src-layout checkout, so installed packages (Nix, pip, wheel) must set `AUTOPIPETTE_REPO_ROOT` to an absolute path (a relative one raises at import; both systemd units set it, see `systemd/README.md`). `ConfigKey` centralizes JSON key name constants; use those instead of hardcoding strings when touching config parsing.

The kiosk (`autopipette_kiosk/main.py`) takes its `REPO_ROOT` from `DefaultPaths.DIR_REPO_ROOT` rather than recomputing it from `__file__` — it used to do the latter, and the copy silently diverged (it missed the `AUTOPIPETTE_REPO_ROOT` override); don't reintroduce a second resolution path. `PROTOCOLS_DIR` (default `REPO_ROOT / "protocols"`, overridable via `AUTOPIPETTE_PROTOCOLS_DIR`) is resolved once at module import time, so changing the env var requires a process restart to take effect.

### Multi-machine config split: shared repo vs. local per-machine root (issue #68)
`config/` (and `protocols/`) above is the **shared code repo**, identical across every rig. Real per-machine data — a rig's actual hostname, its deck layout, its own protocols — lives instead in a second, separate **local config root**, outside the repo entirely and managed as its own git repo by the operator; `tapd`/`tap` never shell out to git for it. It defaults to `$XDG_CONFIG_HOME/tricca-autopipette` (falling back to `~/.config/tricca-autopipette`), overridable via `$AUTOPIPETTE_LOCAL_DIR`, and mirrors the shared categories directly as children (`DefaultPaths.DIR_LOCAL_SYSTEM`/`DIR_LOCAL_GANTRY`/etc., alongside the existing `DIR_CONFIG_*` shared ones). One resolver, `LocalConfigRoots` (`core/pipette_constants.py`, colocated with `DefaultPaths`), implements both merge shapes:
- **`gantry/`, `pipettes/`, `liquids/`, `locations/`, `plates/`, `protocols/`** — union categories: shared ∪ local, same filename in both roots means local wins, `LocalConfigRoots.resolve`/`list_files`. `JsonConfigManager`, `LocationManager`, `daemon/service.py`'s protocol methods, and the kiosk's own `/protocols`/`/run` pre-check all resolve through this — not just `tap`/`tapd`, since the kiosk keeps its own direct-glob listing (see above) and would otherwise silently diverge from what the daemon can actually run.
- **`system/`** — not a union: pick-exactly-one-active-file, 100% local at load time. `JsonConfigManager` resolves system files (including any `extends` ancestor) against `DefaultPaths.DIR_LOCAL_SYSTEM` only; `config/system/default_system.json` in the shared repo is a copy-from template, never read live once a local file exists. `daemon/main.py`'s `resolve_system_config` owns the startup lifecycle this implies: auto-copies the shared template in in when no local config exists yet, `tapd --init-local-config [NAME]` does that on demand and exits, an explicit `--config <name>` always resolves locally and re-points the symlink, more than one local profile with no `--config` prompts interactively when stdin is a TTY (default = last-loaded) and **hard-fails at startup** naming the profiles when it isn't (the normal systemd case) — never guesses, never hangs waiting on input that will never arrive. "Last loaded" is tracked via a plain symlink, `system/active.json` in the local root, not a state file, so it's inspectable/settable with `ls -l`/`ln -sf`.

This split is deliberately provisional for `gantry/`/`pipettes/`/`plates/` — real per-rig divergence there isn't well understood yet, and a future pass may cull those back to shared-only; `locations/`/`protocols/` are expected to stay split. The kiosk gets no new UI for any of this (`tapd`'s own auto-copy/hard-fail startup behavior already covers a kiosk-fronted machine, since `tapd` is headless under the kiosk's systemd chain too); a kiosk config-picker page is issue #33's slice c (the `config.switch_system` RPC it needs exists). See `config/README.md` for the full operator-facing model and `systemd/README.md` for the headless-start caveat.

### Config write-back (`core/config_writer.py`, issue #33 slice a)
The one runtime config writer. `set_config_value(category, filename, key_path, value)` edits one file's **raw, unparsed JSON** at a dotted key path (list indices as integer segments, e.g. `plates.0.x`; every segment but the last must exist): it reads the local copy if there is one else the shared one, mutates the raw dict, validates the result with the same parsers the loaders use (`GantryKinematics`/`PipetteModel`/`LiquidProfile`, a throwaway `LocationManager.apply_locations_data` for `locations`/`plates`, `JsonConfigManager.validate_system_data` for `system` — parse-then-apply, so an edit that wouldn't load raises `ValueError` and writes nothing), then writes to the **local** root via `write_json_atomic` (temp file in the same dir + `fsync` + `os.replace`, writing *through* a symlink such as `system/active.json` rather than replacing it). A shared-only file is thereby copied into the local root on first write (copy-on-write via #68's filename override); the shared repo is never written. It never round-trips through a pydantic model, so unknown keys and `extends` survive — `extends` is simply never resolved on the write path. `system` reads/writes the local file only. Exposed as `AutoPipetteService.set_config_value` / `config.set_value` / `tap`'s `set_config <category> <file> <key.path> <value>` (value parsed as JSON, else taken as a string); it returns `ok=False` rather than raising on a refused write. High-risk numeric fields (gantry speeds/accels, the pipette's syringe volumes/travel/speeds/accels/waits and servo angles) must also stay inside `HIGH_RISK_BOUNDS` (same module, keyed by `(owning model, field)` so a bound applies however the field is reached, and checked leaf by leaf for a whole-block write); it's enforced on write only, so an existing out-of-range file still loads. `tap`'s `settings` lists every editable field with its range and the `set_config` arguments that change it. A *new* leaf key (one not already in the file) is refused unless the category's model defines it (`_check_known_key` walks `SystemConfig`/`GantryKinematics`/`PipetteModel`/`LiquidProfile` fields, stepping through `dict[str, Model]` collections such as a system file's `liquids.<name>`, and treating free-form values — `network`, `LocationsConfig`'s raw sources — as unchecked); pydantic ignores extras, so without this a typo'd field name would be written and silently do nothing. `locations`/`plates` have no model and accept any key. Editing a parent system file doesn't re-validate the children that `extends` it, deliberately: the merge is shallow per top-level key and each key is validated on its own, so a value that loads in the parent loads in every child, and a cycle introduced via `extends` already fails the parent's own validation.

### Live config changes (issue #33 slice b)
A successful write takes effect in the running daemon, no restart. `AutoPipetteService.set_config_value` follows the write with a hot-reload: `locations` → `LocationManager.reload_source(filename)` if the deck holds entries from that file (re-applies only the names it currently sources from it plus new ones, unloads names the file dropped; a name another file overrode is left alone); `plates` → `reload_source` for every `LocationManager.loaded_files()`; everything else → `JsonConfigManager.reload()`. `reload()` rebuilds `SystemConfig` from the manager's *membership inputs* — the active system file (`system_file`, set by `load_system_config`), `_gantry_file`/`_pipette_file` (set by `load_gantry`/`load_pipette`) and `_unloaded_liquids` (set by `unload_liquid`, cleared by `load_liquid`) — reusing the same `_build_system_config`/`load_*` paths startup uses, all-or-nothing. `AutoPipette.apply_config()` then re-derives everything it caches (gantry, pipette model, merged syringe params, volume converter, G-code header; an active liquid that vanished falls back to `water` with a WARNING). Both go through `AutoPipetteService._apply_config_change`, which also rebuilds the deck (`_load_locations(..., replace=True)`) if the system config's `locations` changed. Every deck rebuild runs inside `_preserving_deck_state` (tipbox `snapshot`/`restore` + `snapshot_cursors`/`restore_cursors`), so consumption survives. A `network` edit is written and re-read but the Moonraker connection isn't re-opened: that one needs a `tapd` restart.

Runtime membership, as `AutoPipetteService` methods + `config.*` RPCs + `tap` commands: `unload_liquid <name>` (refuses the active liquid; every liquid file is still loaded at startup), `load_liquid <file>` (as before, now also re-applied live), `load_pipette <file>` (swaps the one active pipette; no unload, since there's always exactly one), `switch_system <file>` (loads a local profile as a fresh start would, dropping runtime loads, and re-points `system/active.json` via `LocalConfigRoots.set_active_system` — #67's live profile switch, e.g. murphy_100 ↔ murphy_1000). `system_summary` reports `system_profile` (active) and `system_profiles` (available). None of the four new commands (`set_config`, `unload_liquid`, `load_pipette`, `switch_system`) is a protocol-file command.

**Forced re-home.** `_apply_config_change` compares `(pipette_model, gantry)` before and after; if either changed — or `switch_system` ran — it sets `AutoPipetteService._homing_invalidated`, which `require_homed` checks *before* Moonraker's `homed_axes` (raising `NotHomedError` with a "homing invalidated by a config change" reason). Only a full `init` or `home all` clears it; homing one axis doesn't. A daemon-side flag rather than emitting `M84` (which would make Klipper itself drop `homed_axes`): it can't race the next `notify_status_update`, needs no connection, and doesn't de-energize the steppers.

**Run-lock.** The `refuse_while_running` decorator on `set_config_value`/`unload_liquid`/`load_pipette`/`switch_system` returns `config_lock_refusal()` — `ok=False` with `data={"reason": "run_active"}` — whenever `RunStatus.config_locked` (status `running`, which lasts until Moonraker reports the print done, not just the replay). `ControlServer` routes these RPCs through `AutoPipetteService.dispatch_config`, which checks *before* waiting on the dispatch lock the replay holds (possibly for a whole breakpoint), so a refusal returns at once. `config_locked` is in `run.status` and every `notify_run_status` push, for clients to grey fields out. `load_liquid`/`load_locations`/`unload_locations` are protocol-file commands and deliberately not locked.

`LocationManager.save_to_json` (the whole-deck `save_locations`) uses `write_json_atomic` too, and remembers each file-loaded location's raw entry (`_raw_entries`, keyed on object identity so re-setting a name interactively silently invalidates it): a loaded entry is written back verbatim (`plate_file` references, unknown keys), with only a tipbox's `tips` block refreshed from current consumption; only locations created/replaced interactively are serialized from their objects. Loading any file under `config/locations/` and saving it reproduces it (`tests/core/test_config_write_back.py`).

### Pipetting technique (air gaps, prewet, capacity)
Technique parameters resolve **explicit CLI flag > active liquid profile > pipette default > 0**, in `AutoPipette.resolve_technique`. The per-command flags (`--pre_air_gap`, `--post_air_gap`, `--prewet`, `--prewet_vol`) and their `*Args` fields are `| None`-typed and default to `None`, so "flag omitted" is distinguishable from an explicit `0` — with plain zero-defaulted floats, `--pre_air_gap 0` could not override a non-zero profile value. For the same reason `get_merged_syringe_params` tests these with `is not None` rather than the `or` used for the older speed/wait keys.

**Naming:** the concept is an *air gap* everywhere — `pre_air_gap`/`post_air_gap`, never `aspirate_air`. It names the thing (a gap of air that persists in the tip through the dispense) rather than the action that created it, and it's the term protocol authors already know. An earlier `pre_aspirate_air`/`post_aspirate_air` spelling from the merged `aspirate-air` branch was renamed out; don't reintroduce it. Microlitre quantities carry a `_ul` suffix on model/dataclass/parameter names but **not** on user-facing flags, which is why `--pre_air_gap`, `--post_air_gap` and `--prewet_vol` set explicit `dest=`s (`pre_air_gap_ul`, …) — the same pattern as the pre-existing `--dispense_vol` → `disp_vol_ul`.

`LiquidProfile` carries `pre_air_gap_ul`/`post_air_gap_ul`/`prewet_cycles`/`prewet_vol_ul` (all `| None` = "defer to the pipette"), and `PipetteSyringeKinematics` carries the non-optional fallbacks. `_update_syringe_params` must copy every one of these onto `self.syringe` — it silently dropping fields is what previously made `air_gap_ul` and `prewet_recommended` inert config that `ls` displayed but nothing applied.

`AutoPipette.fit_air_volumes` reconciles `pre + volume + post` against `usable_capacity_ul()` (`max_volume_ul - capacity_margin_ul`, the latter a config field replacing an earlier hard-coded `+2` µL fudge). It fits the **post**-gap first — that is the anti-drip cushion at the tip orifice — and shrinks the pre-gap for whatever is left, logging a WARNING naming requested vs applied. It raises `VolumeCapacityError` only when the *liquid alone* doesn't fit, since shrinking air can't rescue that and quietly aspirating less would deliver the wrong amount. `pipette()`'s chunking subtracts the air overhead from the per-chunk budget, or every full chunk would overflow by exactly that much.

Because the post-aspirate cushion sits between the liquid and the orifice, a metered dispense has to drive it out ahead of the liquid — `dispense_volume(purge_air_gap_ul=...)`. The dispense-everything path (`clear_syringe()`) doesn't need this.

There is deliberately **no** blowout support and **no** touch-off: both existed as config/flags (`speed_blowout`, `blowout_recommended`, `--touch` wired to a `pass  # TODO`) that nothing implemented, and were removed rather than left looking live. Neither legacy branch has a real implementation to port.

#### Multi-dispense (`--splits`)
`pipette --splits 'plate_a:12@A1;plate_b:8@C3'` does one aspirate then N metered dispenses (`AutoPipette.pipette_splits`), saving a tip pickup and a source trip per destination. Ported from `origin/sticky-test-scott`'s `pipette_splits`, but addressing wells by ID through `traversal.well_id_to_rc` rather than that branch's `@ROW,COL` integers; `@WELL` is optional and omitting it defers to the plate's own `TraversalOrder`. Parsing is in `core/splits.py` (syntax only); `AutoPipette.resolve_splits` validates against the deck and runs **before any G-code is emitted**, matching `LocationManager.load_from_json`'s parse-then-apply rule — a bad spec must not strand a half-dispensed tip mid-plate.

Unlike `pipette`, this never chunks: the whole volume must fit in the syringe at once, since a single aspirate is the point.

Leftover liquid requires an explicit `--leftover keep|waste`; omitting it is an error rather than the silent `keep` the original defaulted to. `waste` verifies the waste container up front. A tip still holding liquid (`keep`) is always retained regardless of `tip_end` — never put down a tip with liquid in it.

#### Auxiliary triggers (`trigger`)
`trigger <channel> on|off` (issue #16) drives auxiliary hardware (air, shake, lid, …) through a Klipper `[output_pin]`. Channels are per-machine wiring: `SystemConfig.trigger_pins` (`dict[str, str]`, alias → pin name, empty by default) is the only source of valid channels — there is no global channel list. `AutoPipetteService.trigger` validates against that map (`Invalid channel 'lid'. Valid: air, shake`, or `Valid: (none configured)`) and `on`/`off` only, then calls `AutoPipette.set_trigger`, which emits `M400` **then** `SET_PIN PIN=<pin> VALUE=1|0` — `SET_PIN` isn't a motion command, so without the `M400` first the pin can flip while an already-queued move is still running. Deliberately ungated (no `require_homed`: it doesn't move the gantry) and fire-and-forget (no daemon-side record of the last commanded state, so nothing turns a trigger off at protocol end).

### Domain model (`core/`)
- `autopipette.py` — `AutoPipette`: central controller tying config, location manager, G-code buffer, and volume converter together; owns `pipette()`/`aspirate()`/`dispense()`/tip-handling and multi-liquid switching (`switch_liquid`).
- `pipette_models.py` — pydantic-style dataclasses for `SystemConfig`, `GantryKinematics`, `PipetteModel`, `PipetteSyringeKinematics`, `PipetteState`, `TipState`, `TipSlotState`, the `TipEnd` literal, `FluidDisplacement`.
- `volume_converter.py` — `VolumeConverter.vol_to_mm`/`mm_to_vol`: volume (µL) ↔ plunger travel in **millimetres** (the unit Klipper's `MANUAL_STEPPER` takes for `MOVE`, with `SPEED` in mm/s and `ACCEL` in mm/s²), fit from a pipette's or liquid's `calibration_volumes`/`calibration_mm`. These are **real plunger millimetres**, which holds only because the rig's Klipper config sets `[manual_stepper pipette_stepper] rotation_distance: 2` (NEMA-17 on a single-start T8 lead screw, 2 mm lead). Before issue #29 the rigs ran `rotation_distance: 8`, so every syringe distance/speed/accel in `config/pipettes`/`config/liquids` (and the `PipetteSyringeKinematics` defaults) was 4× inflated; #29 rescaled them all by exactly 0.25, so this repo and that Klipper setting must change together on a rig. Exposed as the `util.vol_to_mm`/`util.mm_to_vol` RPCs and `tap` commands of the same names (renamed from `vol_to_steps`/`steps_to_vol`, issue #29 — hard rename, no alias). `AutoPipette.operate_syringe` refuses a volume the curve maps to negative travel, since that would flip the MOVE's direction.
- `coordinate.py` — `Coordinate`, used throughout for absolute/relative XYZ positions.
- `well.py` — `Well`, `StrategyType` (dipping/aspirate strategies per well).
- `plates.py` — plate class hierarchy + `PlateFactory` registry (`@PlateFactory.register(...)`-style pattern, generic in the decorated subclass so `TipBox`-specific methods stay visible to type checkers — check the file before adding a new plate type). Wells are always stored row-major in `Plate.wells`; the *visiting* order is a separate `Plate.sequence` of flat indices, and `Plate.curr` is a cursor into that sequence, not into `wells`. With the defaults (`row_major`, no mask) the sequence is the identity, which is what keeps existing behavior unchanged.
- `traversal.py` — well addressing (`A1`/`H12`/`A1:D6` ↔ flat indices), `TraversalOrder` (four orthogonal fields: `major`/`row_dir`/`col_dir`/`serpentine`, covering every raster and serpentine walk as *data* rather than code), `TraversalRegistry` of readable preset names for config files, and `WellMask` for restricting a plate to a sub-region. Ordering decides sequence, masking decides membership — masking never reorders the survivors.
- `splits.py` — `Split`, `LeftoverAction`, and `parse_splits_spec` for the `pipette --splits` mini-language. Syntax only; deck validation lives in `AutoPipette.resolve_splits` (see "Multi-dispense" above). Kept out of `commands/tap_cmd_parsers.py` because the domain layer is what validates against the deck, and `commands/` imports from `core/`, not the reverse.
- `tipbox_manager.py` — `TipBoxManager`: owns several independent `TipBox`es and decides which supplies the next tip, drawing in registration order (which `LocationManager` takes from config-file order). Boxes are never merged: an earlier `TipBox.append_box` spliced their well lists together, which destroyed per-box provenance and made unloading, per-box counts, and persistence impossible. Each box tracks a per-position `TipSlotState` and raises `OutOfTipsError` rather than reissuing a used tip; `snapshot`/`restore` move that state through Moonraker's DB, and `restore` refuses a record whose plate dimensions no longer match rather than misaligning consumed positions onto different physical wells.
- `pipette_exceptions.py` — domain exceptions (`NoTipboxError`, `OutOfTipsError`, `TipAlreadyOnError`, `NotALocationError`, etc.), plus two daemon/service-lifecycle signals kept here to avoid an import cycle with `commands/*.py` (see that module's docstrings for why): `NotHomedError` (the homed-interlock's exception) and `ProtocolAbortedError` (raised when a `break` line's breakpoint is answered "abort"). Prefer raising/catching these over generic exceptions in this layer.
- `gcode_commands.py` — `GCodeCommands` (issue #30): pure builders for Klipper's documented built-in G-code, the same "no I/O" shape as `MoonrakerRequests`/`ControlRequests` a third time. Every G-code line `AutoPipette` emits comes from one of these — there are no hand-built f-strings left in `autopipette.py`. The catalog is deliberately wider than today's callers: motion/modes (`G1`, `G90`/`G91`, `G28`, `G4`, `M117`, `M220`, `M400`, `M84`, `QUERY_ENDSTOPS` — the documented spelling of `M119`, `SET_VELOCITY_LIMIT`), `MANUAL_STEPPER` (plain/`STOP_ON_ENDSTOP` in the documented string forms only — `StopOnEndstop` deliberately rejects Klipper's numeric aliases, which Klipper logs a deprecation warning for on every call, issue #29 — plus the `GCODE_AXIS` form) and `STEPPER_BUZZ`, `SET_SERVO`, `SET_PIN` (value/`CYCLE_TIME`/`TEMPLATE`), `SET_LED`/`SET_LED_TEMPLATE`, `SET_FAN_SPEED` (+template)/`SET_TEMPERATURE_FAN_TARGET`, `LOAD_CELL_*`, `QUERY_ADC`. Builders validate only what the Python layer alone knows — that the output stays one line (a config name or `M117` message with a newline raises; a config name with a space is `shlex`-quoted, matching how Klipper parses extended parameters) and that template parameters get the `PARAM_` prefix Klipper otherwise silently drops — never bounds Klipper's own per-machine config already enforces (servo angle range, LED 0–1 levels), and never whether a module is configured at all (callers check names against their own config first). Builders return `GCode = NewType("GCode", str)`, and `GCodeBuffer.add`/`GCodeManager.add_gcode`/`AutoPipetteService.output_gcode` only accept `GCode`, so a stray f-string is a pyright error; the escape hatch is an explicit `GCode(...)` cast, used today only for comment lines (`GCodeBuffer.add_comment`, the `pipette` command's header comment in `service.py`). `tests/core/test_autopipette_gcode_emission.py` pins every emission site's exact text against a golden file.
- `gcode_buffer.py` — low-level G-code line accumulation used by `AutoPipette` and `GCodeManager`'s batch mode; accepts only `GCode`.

### Moonraker/WebSocket layer (`moonraker/`)
- `websocket_client.py` — `WebSocketClient` runs an asyncio event loop on a background thread; public API is synchronous (`send_jsonrpc`, `wait_for_connection`, context-manager support) with a `Queue`-based `MessageType` (`fatal_error`/`error`/`handler_error`/`notification`/`parse_error`) for async notifications/errors surfaced back to the shell.
- `moonraker_requests.py` — `MoonrakerRequests`: pure builders for Moonraker JSON-RPC payloads (printer control, file upload/print-start, etc.) — no I/O itself.
